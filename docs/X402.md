# X402 — the payment rail

Read before any payment work. `CLAUDE.md`: **never write a custom
payment/deposit function.** If you are writing `deposit()`, the answer is here
instead.

## The one idea

x402 turns payment into an HTTP status code. A route answers `402` with payment
requirements; the client signs an EIP-3009 authorization; a facilitator verifies
it and settles on-chain; the route runs. There is no billing system, no approval
step, and no gas prompt for the payer.

**`payTo` is the Suite contract.** That is the whole reason the pool needs no
deposit function: x402 moves the settlement token straight to that address. The
pool cannot see individual payments (EIP-3009 has no recipient callback) and does
not need to — it sees its own balance, and the split is computed off-chain.

## Where it lives

| File | Role |
|---|---|
| `apps/web/app/api/protected/route.ts` | The paid route. `withX402(handler, payTo, route, facilitator)` |
| `apps/web/lib/x402.ts` | `payToAddress()`, `facilitatorConfig()`, `KOHA_ROUTE` |
| `apps/web/lib/settlement.ts` | Settlement-token configuration + validation (server only) |
| `apps/web/components/contribute-button.tsx` | Client side, `wrapFetchWithPayment` from `x402-fetch` |

Network is `avalanche-fuji` throughout. Settlement is the **settlement token**:
dNZD in the end state, Fuji USDC as the temporary fallback.

## The rules

1. **`payTo` must be the deployed Suite contract.** `X402_PAY_TO` exists to point
   at a dev wallet *before* the contract is deployed, because `addresses.json`
   still holds a zero address. Once Suite is deployed, either set `X402_PAY_TO`
   to the Suite address or unset it and let `addresses.json` supply it. Never
   leave it pointed at a personal wallet during a demo.
2. **No custom payment plumbing.** No `deposit()`, no `contribute()`, no
   transfer-then-record. The rail does it.
3. **Settlement happens only after a `<400` response** — `withX402` settles after
   the handler succeeds, so a failed request does not charge.
4. **Server-only config.** Nothing about the facilitator or the price carries a
   `NEXT_PUBLIC_` prefix. A facilitator secret must never reach the browser.

## Pricing modes

`KOHA_ROUTE.price` comes from `settlementPrice()` in `lib/settlement.ts`, which
has exactly two modes.

**Fallback (nothing configured).** The price is a money string — `X402_PRICE`,
default `"$0.01"` — and x402 resolves the network's default asset itself. For
`avalanche-fuji` that is `0x5425890298aed601595a70AB815c96711a31Bc65`, 6
decimals, EIP-712 domain `{ name: "USD Coin", version: "2" }` (x402's own
`getDefaultAsset`, not our guess). This is what local testing uses and it is
unchanged from before the token work.

**Explicit token.** Set all five and the route quotes that token directly:

```dotenv
X402_SETTLEMENT_TOKEN_ADDRESS=
X402_SETTLEMENT_TOKEN_DECIMALS=
X402_SETTLEMENT_TOKEN_EIP712_NAME=
X402_SETTLEMENT_TOKEN_EIP712_VERSION=
X402_PRICE_ATOMIC=
```

Deliberate choices in that validator:

- **Partial configuration is a boot error**, not a silent fallback to USDC.
  Settling in the wrong currency on stage is worse than failing to start.
- **`X402_PRICE_ATOMIC` is atomic units, not dollars.** Deriving a dNZD amount
  from `"$0.01"` would invent an NZD/USD exchange rate. It is a human input.
- **`X402_SETTLEMENT_AUTHORIZATION` is validated against `eip3009`.** x402's
  exact-EVM scheme relays `transferWithAuthorization` only — that is also what
  makes the payment gasless.

The token's decimals and EIP-712 domain must match the deployed token contract
exactly. A wrong domain means the payer signs something the token will reject at
settlement, which surfaces as a confusing facilitator error, not a clear one.

## dNZD — answered, and the answer is no (for now)

The open question in an earlier draft of this doc has been resolved by inspecting
the deployed contract. **dNZD does not implement EIP-3009, so it cannot settle
over x402 today.** Full evidence and method: **`docs/DNZD.md`**.

Confirmed and recorded in `packages/shared/src/settlement.json` under
`candidates.dNZD`: address `0x99A22a5AD6B2fd7EefE512F49dc22336dEEdf877`, 6
decimals, EIP-712 domain `{ name: "dNZD", version: "1" }`. Status stays
**pending** — the metadata is known, the rail support is not there.

Why `permit` does not rescue it: ERC-2612 `permit` is implemented (verified with a
valid signature), but it only sets an allowance. Something still has to call
`transferFrom` and pay gas. x402's whole value is that the payer signs once and
pays no gas, which is what EIP-3009's `transferWithAuthorization` gives in a
single transaction. Bridging `permit` into the rail means writing a new x402
scheme, which is well outside this weekend — see `docs/SCOPE.md`.

What still works with dNZD: the **pool and the split**. `Suite` only calls
`balanceOf`/`transfer`, so it holds dNZD fine and flow 3 settles on-chain
normally. Only flow 2, the gasless micropayment, is blocked.

## Facilitator

`X402_FACILITATOR_URL` unset → the x402-next default (x402.org, testnet). For
real Fuji settlement, `ARCHITECTURE.md` picks the thirdweb facilitator because it
settles Avalanche C-Chain. If it requires auth, extend `facilitatorConfig()` with
`createAuthHeaders` using `THIRDWEB_SECRET_KEY` — do not put the key in the URL.

Status: **pending.** thirdweb is not configured because the available plan
appears paid. Until a facilitator is set, the unpaid 402 works and a paid
settlement does not.

## The smoke test

```bash
pnpm dev
curl -i http://localhost:3000/api/protected     # -> HTTP 402 + requirements
```

Then, with a funded wallet, click "Contribute koha" in the dashboard and check
that the balance at `payTo` increased and that `x-payment-response` carries a
transaction hash. The full paid path needs: a facilitator URL, the settlement
token in the payer wallet, and `payTo` set to a real address.

## Gotcha that is not ours to fix

`next.config.mjs` carries a `webpack.IgnorePlugin` for `^@x402/`. wagmi's
connector barrel transitively references optional `@x402/*` server-signing
packages that are not installed. It is required as long as wagmi is a
dependency — **do not remove it.**
